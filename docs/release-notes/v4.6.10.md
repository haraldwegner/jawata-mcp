# jawata-mcp v4.6.10

**A worker briefed to build must write its test first, the files a hired agent may write are stated once, and the editor's folders follow the editor window.** This release is what jawata-studio 4.6.12 and jawata-chat 0.2.10 need.

## What changes

- **Test first is enforced.** A worker briefed with a BUILD instruction must write its test, see it fail, and only then write the code; a code change by a shell command or a patch counts too. A run that breaks the order is reported with the first open step it broke, and the report does not claim a test passed when no test result was shown. The empty stub a test needs is added with `generate(kind=add_method)`.
- **The main seat leaves no code behind.** Code the main seat's brain wrote to the folder by any means is read from the folder and put back, and the answer says what was put back. A hired lead's code is put back the same way.
- **A document that tells an agent what it may do** (`CLAUDE.md`, a seat, a skill) is code to a lead's own editor. The `files` tool writes and edits text documents (`.md`, `.csv`, `.txt`, `.html` and the like), not only `.md`; one rule in one place decides it, and it judges a path as spelled and as the place a link really leads.
- **Access follows the workspace on disk, whichever starts first.** The engine reads the list of folders each editor window keeps on every call, so a folder a window opens after a hired brain started is reachable and a closed one is not. A brain the engine starts is told which folders its guard allows, from one reading, and that file is rewritten as projects load and unload.
- **A lead's inbox.** A lead waits for its hires only while its brain lives; a report for a brain that died goes up to whoever hired the lead, and a report that comes after the brain's turns are over is held and told to its lead, not lost.
- **The observer answers by point number.** A verdict answers one flag by its number, so two flags about no instruction are told apart; a verdict with no number judges nothing.
- **A path no Java tool resolved is answered once, by what is true:** not there is `FILE_NOT_FOUND`, there but no Java source is `NOT_A_JAVA_SOURCE`, outside every loaded project is `NOT_A_JAVA_PROJECT`. The generate door gives the same answer for every kind.
- **`generate` can add a method** (`kind=add_method`): a stub that throws `UnsupportedOperationException` on a class and a bare signature on an interface.
- **The duplicate check offers only jobs the loaded workspace holds,** and says how many nominees it left out because they are outside it.
- **A type two loaded projects hold, one as source and one as the engine's own jar, resolves to the source.**
- **A hired Claude session loads only the person's own settings and refuses the bypass permission mode,** so a project's `.claude` settings cannot widen what a hire may do.
- **Cursor as main seat or lead keeps `hire`,** and what it writes with its own editor outside documents is read as a breach.
- `GitTool` refuses the same agent names the studio's commit hook refuses as co-authors.

## Known limits

- The test-first rule was met live in a Linux run with Claude as the hired brain; the other items are covered by tests. Windows and macOS are run by CI, not by hand.
- Two items of Agent Control are not built: calls that cannot be tied to a run shown as unassigned, and a client the hook does not watch shown as not observed (ledger row 28h-C27-11).
- `SourceRootResolutionTest` failed twice in whole-suite runs and passed alone; its cause is not found, and its failure message now says what the project model held (row 28h-S19-12).
- Other Java tools that answer for an unresolved path were not each tested; the generate door and `analyze_file` were.
- The known unfixed limits listed in the 4.6.7 notes stand.
