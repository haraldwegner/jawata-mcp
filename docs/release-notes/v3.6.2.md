# jawata v3.6.2

**This finishes what v3.6.1 started, and corrects what its notes claimed.**

v3.6.1 said it made a project's own source folders visible — so that tests in a
folder named `test/` would be found and quality scans would stop missing them.
Working it in anger showed that was only half true, in the half that matters
least.

## What was actually wrong

There were **two** copies of the routine that turns a file path into something
the compiler understands. Which one runs depends on how a tool is called:

- ask a question **without naming a project** → the first copy
- ask the **same question about a specific project** → the second copy

v3.6.1 fixed the first and left the second untouched. Naming the project is the
normal way an assistant asks about one project in a workspace of many, so in
practice the fix almost never ran.

The effect on a real 1040-file Eclipse plug-in project, two calls seconds apart
against the same running server:

| the question | the answer |
|---|---|
| "find the tests" | found them |
| "find the tests **in this project**" | **1 of 126** |

The scans behave the same way, and they always name the project — which is why
they kept reporting 142 unreadable files, every one of them in the `test/`
folder.

## The fix

The duplicate is gone. There is now one routine, used by both kinds of call, so
naming a project can no longer change what gets found. The two cannot drift
apart again, because there is no longer a second copy to forget.

A second problem in the same place: when listing a project's files failed, that
view returned whatever it had managed to collect and said nothing — a partial
list that reads exactly like a complete one, which is how a scan comes to report
"nothing found" about files it never opened. It now reports the failure instead
of quietly shrinking the answer.

## Correcting the v3.6.1 notes

The v3.6.1 notes state that files in a `test/` folder became visible to test
discovery and the quality scans. **For anything that named a project — which is
the common case — that did not happen.** The other fix in v3.6.1 (search results
that pointed at a folder instead of a file) was real and unaffected.

If you read those notes and concluded your plug-in projects were fixed, they
were not until this release.

## Verification

Full suite 1689 of 1691 passed, 0 failed (2 are skipped without a private corpus
and say so). End-to-end suite against the built artifact: 36 of 36.

Ten new tests, four of which exercise the project-scoped path directly. That
path had **no tests at all**, which is how a shipped fix could do nothing while
1681 tests stayed green. Those four were run against the unfixed build first:
three fail without the fix, including one that reproduces the field symptom —
a file the scan lists and then cannot open.

Nothing about recall, the experience store, or the tool set changed; the tool
count stays 45.
