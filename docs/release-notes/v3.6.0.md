# jawata v3.6.0

Sprint 28 (client + OS coverage) opens here. A macOS retest on a real Eclipse
plug-in project found that most of the project's build path never reached the
compiler. This release carries it across.

Ships alongside **JAWATA Studio v3.6.0**, which fixes a runtime update that
could not complete and a deploy target that could never be selected. See that
release's notes.

## Eclipse plug-in projects lost most of their build path

To analyse a project, jawata builds a private copy of it. On Eclipse plug-in
projects two things it needed were being thrown away without a word.

**Required projects.** A project that declares five dependencies on sibling
projects in the same workspace reached the compiler with one. Eclipse records
those dependencies in the same place it records folders of source code,
distinguished only by how the path is written — and jawata read every one of
them as a folder. A dependency on another project is not a folder, so it was
looked for on disk, not found, and dropped in silence. They are now recognised
for what they are and resolved against the other projects in the workspace.

**The JUnit libraries.** `find_tests` reported no tests at all on a project
with three folders of tests. Eclipse names the JUnit libraries indirectly and
fills them in when it opens a project; jawata's private copy left that entry
out entirely, so the annotations that mark a test meant nothing to the compiler
and nothing was recognised as a test. The JUnit libraries are now supplied,
matching the JUnit version the project asks for — and when a project does not
say which version it wants, both are supplied rather than guessing, since a
spare library on the build path is harmless and a missing one silently breaks
every test lookup.

Together with the default-Java-runtime fix in v3.5.0, this closes the reported
build-path loss on plug-in projects. One item is deliberately left alone: the
list of plug-ins a project requires is still resolved from the project's own
manifest against jawata's bundle pools, which is the mechanism that replaces
Eclipse's own, not a gap.

**What this changes for you.** On an Eclipse plug-in project, "does this
compile" and "what are the errors" can now actually be answered, and test
discovery works. Before this, a clean compile result on such a project meant
only that the compiler had refused to start — which is a far worse answer than
an error, because it looks like success.
