# jawata-mcp v4.1.3

One fix, and it is the one v4.1.1 and v4.1.2 were both meant to be: a project that declares
no Java language level now resolves modern syntax on macOS.

## The workspace level never rose to the JDK's on macOS

Two fork-slice rows failed on the macOS matrix job and passed on Linux in the same run — at
v4.1.0, v4.1.1 and v4.1.2, with identical messages: a record type reported as missing, and
a method whose signature named it refusing with "Cannot resolve binding of enclosing method
declaration". Both rows use the one vendored slice that declares a record and carries no
build file, so it takes the workspace's default language level.

That default is not the same on the two platforms, and the reason is how the JDK gets
registered. On Linux and Windows, JDT's launching plug-in detects the running JVM itself and
raises the workspace level to its version. On macOS its standard VM type detects nothing, so
jawata's own fallback registers the running JVM as the default VM (jawata-mcp#3) — and
registered it without the level. The workspace stayed at JDT's built-in default, under which
a record does not parse. Every other fixture in the suite declares its level in a build file,
which is why only this slice could show it.

The fallback now raises the workspace level to the running JVM's own
`java.specification.version` after registering it, exactly as JDT does where it detects the
JVM. It never lowers a workspace already at or above that level.

## Reproduced here, not only on the platform

The failure is reproduced on Linux by `BuildSystemLoadTest`: lower the workspace to JDT's
built-in level, load the record slice, and the method's binding is null — the macOS state.
Raise it as the fallback now does, and it resolves. `ProjectImporterDefaultVmTest` pins the
raise itself. Neither could have been written for the two earlier patches, because neither
patch had found this.

## What the two earlier patches were

v4.1.1 settled the Java model before reading a created file's errors, and v4.1.2 retried a
file lookup through the canonical path. Both fixes stand — the v4.1.2 control ran and passed
on macOS in the very run where these two rows still failed — and neither touched this.
