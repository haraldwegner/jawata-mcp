# jawata-mcp v4.2.1

Five issues, and the ones that changed most were the ones that turned out not to need a
patch. This release is mostly about answers a caller could not act on: a composite nobody
verified, a refusal pointing at the wrong thing, and a setting nobody stated.

## A recipe verifies the state it leaves, and says what it did

`compose_method` and `decompose_conditional` reported `applied: true` over a final state
nothing had looked at, and returned no diff. Every recipe step runs under a gate that
tolerates an intermediate red state on purpose — Replace Temp with Query extracts a method
nothing calls yet — and the engine's own comment claimed the rest was covered by "the whole
composite the caller applies". No caller applies one: by the time the engine returns it has
performed every step, so the composite it hands back is an UNDO.

Both operations now carry `compileVerified`, `introducedErrors` and a `diff`. Errors are
counted as INTRODUCED rather than present — measured per file against the state when the
recipe first touched it — so a recipe run on an already-broken file is not charged with damage
it did not do.

## A refusal whose arguments were fine stops calling itself an invalid parameter

Pointed at a static utility class, `inline kind=class` refused with `INVALID_PARAMETER` and
the hint "check the tool's inputSchema for the required parameters". Nothing in the schema was
wrong: the position was valid and resolved to exactly the class meant, and no argument could
change the fact that a class reached by type name is never held as a field. An agent following
that hint re-reads a schema in which nothing is wrong and calls again.

`PRECONDITION_NOT_MET` says what happened — the arguments were valid and resolved, and the
operation does not apply to the code they name — and its hint says re-reading the schema will
not help. It requires a reason code, because the point of the code is to be branched on.

The local field recording ranked this the largest CURRENT failure class independently: of 52
failures in three days, seventeen were `INVALID_PARAMETER` on refactoring doors.

## `lazy_class` can reach the second fix it offers

The smell declares two cures and tells them apart — fold the class into its user, or into its
parent. Measured: the detector returned early for any type with a declared superclass, and the
subclass cure refuses exactly the complement. The same AST predicate read with opposite
polarity, so one of the two could never fire on anything this detector emits, and a reader
given both was sent between two operations pointing at each other.

A subclass that overrides nothing is Lazy Element in Fowler's own terms, and it is now
reported. One that overrides is not — that control is what keeps this from becoming "report
every subclass".

## The Eclipse settings this product depends on are stated

jawata runs inside an Eclipse workspace and read settings it never wrote, so every platform
default was a latent defect waiting for the host that differs — three shipped defects already,
each found on whichever platform's default happened to differ, one of them costing three
releases.

`WorkspaceSettings` states them: what each is set to, why the product depends on it, and who
writes it. Applying the same method found a fourth instance before it became a bug report —
the workspace default charset was never set, so JDT decoded source with the platform charset
while jawata read it as UTF-8 everywhere.

## Two questions answered by measurement rather than code

**The line delimiter.** The open report described CRLF written into an LF file and recorded its
discriminating step as never run, because it was framed as needing Windows. That framing is
wrong about where the mismatch lives: it is between the FILE's delimiter and the writer's, not
between two operating systems, so a CRLF file on Linux exercises it. Run — it does not
reproduce. Both writers tested follow the file, and a byte-level gate on two of them now says
so, because the parity goldens compare stripped, sorted lines and are blind to delimiters by
construction.

**Recall failures.** Reported as 59% of all recorded tool failures, with the note that the
instrument could not say whether that was current. That window shipped in 4.2.0: over the
lifetime the shape is 325 of 579 failures, over the last three days it is 2 of 52. A lifetime
artifact of a shape that had already stopped.
