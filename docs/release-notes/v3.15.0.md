# v3.15.0 — a curated store stays curated, and knowledge carries its diagnosis

## The cause becomes first-class

Knowledge convinces the way a story does: situation → complication → solution,
and whether it worked. The store carried three of the four — the complication
(the CAUSE) lived buried in prose, unqueryable.

The distinction matters because one symptom has many causes: a fast heartbeat
can mean you are running, having a heart attack, or fighting a virus — and the
cure binds to the cause, never to the symptom. In code: "constructing a new
object" with *many variations* wants a Factory; the same situation with *many
fields to initialize* wants a Builder. The cause is what tells same-situation
entries apart.

Schema v15 adds the `cause` column, delivered whole:

- **Writers**: `experience(kind=record, cause=…)`, and the md ingest reads
  `cause:` — or `complication:`, the triad's own word — from frontmatter.
- **Reader**: every recall renders the cause beside the situation, so a
  symptom-recall returning several entries reads as a proper differential.
- **Carriage**: export, import and orphan recovery carry it verbatim
  (version-gated for older stores).
- **Never derived**: a legacy row keeps an honest NULL. Splitting causes out of
  existing summary prose is editorial work, not a migration.

Declared follow-up, not slipped in: the recall *shows* the cause; a ranking
that *weighs* it is future work.

## Tombstones: what you remove does not come back

Removing knowledge from the store never held. The studio re-seeds the knowledge
store after every agent deploy, and the only brake on that crawl asked the
STORE — "do I already have this file?" After a deliberate rebuild the store is
empty, so every previously-removed source answered "no", and the whole old
corpus walked back in. Measured on one machine: 413 rows re-imported the day
after a clean rebuild, and one more the next morning. Curation could not stick,
for anybody.

A reseed now REMEMBERS WHAT IT LEFT OUT. Every source the store held that the
reseed did not re-ingest gets a tombstone — a permanent "this file is not part
of this store" marker, stored beside the knowledge and keyed on the file itself:

- **Every later crawl skips it**, including the deploy-time auto-seed, and says
  so: the load report carries a `tombstoned` count and `stats` shows the total.
  A curation that held and a mechanism that is missing can never read alike.
- **Keyed on the source, not its content.** A tombstone keyed on a content hash
  would expire the moment the file was edited, and the store would re-pollute
  gradually instead of at once.
- **Revival is as deliberate as removal**: reseed a root that CONTAINS the file
  and it is ingested again, tombstone cleared.
- **A second reseed keeps the first one's decisions.** Reseed is the routine
  repair; without this it would erase its own curation every time it ran.
- **A bare `wipe` clears tombstones too** — wipe means "empty store, fresh
  world", reseed means "curated rebuild", and the two must not be one act.

Tombstones are machine-local derived state, regenerated by each store's own
reseed, so export and import deliberately do not carry them.

Schema v14 adds the `experience_tombstone` table. Existing stores upgrade in
place on first open; older stores are untouched until then.
