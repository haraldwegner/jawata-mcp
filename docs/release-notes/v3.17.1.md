# v3.17.1 — `stats` reports what the store knows, and touches no disk

A hotfix on v3.17.0. One method is deleted, and with it a defect that could saturate a
developer machine for as long as a window stayed open.

## What happened

v3.17.0 added a drift check to the substrate block of `experience(kind=stats)`: it
walked the substrate root and counted markdown files no row cited, so a story written
and never reseeded in could not stay invisible. The intent was sound. Three properties
of how it was built were not, and they only meet on a real machine:

1. **The root is derived, not configured.** `substrateBlock` computes it as the common
   ancestor of every ingested entry's `memory:` source path. With entries loaded from
   `~/.claude/…`, `~/CursorProjects/…` and `~/Projects/…`, that ancestor is the user's
   **home directory**.
2. **The walk had no bound.** `Files.walk(root)`, every level, every file — while the
   javadoc four lines above claimed *"Read-only and bounded: it lists the ROOT's own
   markdown files"*, which describes `Files.list` at depth 1. Across the whole engine
   this was the only uncapped walk; the substrate loader it reports on already takes a
   depth cap and a non-recursive mode.
3. **It rode the liveness path.** jawata-studio calls `stats` on a five-second timeout
   for one purpose — to learn whether the resident answers at all. Abandoning that
   request does not cancel the resident's work, so each timeout left a scan running and
   the retry started another.

Measured on 2026-08-29 with a thread dump: **64 of 68 HTTP worker threads inside the
walk, in each of three residents**. Twenty cores at 100%, load average 114, and the
"Store unreachable" banner was itself the thing generating the load that produced it.

## The fix

`ExperienceTool.addDrift` is deleted, along with its call. The substrate block still
reports `root`, `derivedFrom` and `howToAdd` — all computed from entries already in
memory, no disk access.

The rule this settles: **`stats` reports what the store knows about itself.** A
filesystem scan is not a store statistic, and a call the client uses as a liveness
probe must answer in milliseconds.

## Why the tests were green throughout

`SubstrateDriftTest` drove the check against a `@TempDir` holding two files, where the
walk is instant. The fixture made the defect invisible by construction — the feature
was only ever exercised on a directory small enough to hide what it did on a real one.

Its replacement, `SubstrateRootTest`, asserts the absence behaviourally: it puts an
unloaded file exactly where the old check would have found one, first proving a root
was derived so the absence cannot pass for the wrong reason, and requires that `stats`
does not report it. It goes red the moment a walk returns to this path, under any name.

## What you lose, and it is real

Nothing now warns that a story file was written and never reseeded in. That protection
was worth having; it was implemented on the wrong call, against an unbounded root. If it
returns it will be on a deliberate call, against a scope someone chose.

## Compatibility

No schema change. The `substrate` block of a `stats` response no longer carries
`unloadedFiles`, `unloaded`, `unloadedTruncated` or `driftWarning`. No shipped consumer
read them — jawata-studio never did.
