# jawata v3.6.1

The v3.6.0 dogfood patch. v3.6.0 restored the build path on Eclipse plug-in
projects; working it in anger on a real 1040-source plug-in immediately showed
that the *answers* were still wrong — jawata could compile the project but
could not read most of its test folder.

## Files in a test folder were invisible

`find_tests` reported **one** test class on a project with more than twenty.
The quality scans reported **142 of 1040 files missed**. Every missed file was
in the project's `test/` folder.

The scans said so out loud — that is why this was findable at all — but the
answers were useless, and "1 test class" is the kind of wrong answer that reads
like a fact.

**The cause.** To turn a file path into a type, jawata guessed which part of the
path was the source folder, using a fixed list of layouts: `src/main/java`,
`src/test/java`, the Kotlin pair, and a bare `src`. Those are Maven and Gradle
conventions. An Eclipse plug-in project keeps its tests in a top-level `test/`
folder, which matches none of them — so the whole path was treated as a package
name and every lookup in that folder failed.

**The fix.** Stop guessing. The project already tells us where its source
folders are, whatever they are called, so ask it. The convention list stays
underneath only as a fallback for paths the project cannot place.

This affects any project with a source folder outside the Maven/Gradle
conventions — `test/`, `tests/`, `integration-tests/`, generated-source folders
— not only Eclipse plug-in projects.

Measured on the fixture that reproduces it, through the running server:
before, 2 files listed and 1 read, the `test/` file reported unreadable; after,
2 listed and 2 read, with nothing missed.

## Search results that pointed at a folder

A search result whose location could not be worked out was reported with the
**project directory** in its file path and no line number. It looked like a
result and pointed nowhere.

This is the same fault v3.6.0 fixed for "find references", in a different
place: it sits in the code shared by six search tools, so all six carried it.

A result is now only given a file path when it really is a file. When the
location cannot be worked out, the result says so — it is neither dropped nor
dressed up as an answer. Dropping it silently would be the worse of the two,
and is the failure this project keeps hunting: a lookup that failed, handed
back as though nothing were wrong.

## Verification

Full test suite 1679 of 1681 passed, 0 failed (2 are skipped without a private
corpus and report themselves as skipped). End-to-end suite against the built
artifact: 36 of 36. Four new tests cover the source-folder fix, and they were
checked against the unfixed build first to confirm they actually catch it —
2 of the 4 fail without the fix, including the exact file that failed in the
field.

Nothing about recall, the experience store, or the tool set changed; the tool
count stays 45.
