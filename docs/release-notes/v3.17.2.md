# v3.17.2 — the hollow-wiring gate stops discarding the error that explains its own failure

**No Java changed since v3.17.1.** The engine this release ships is byte-identical in
behaviour; one build gate script is repaired. It is versioned so the running fleet has a
release to move to.

## What was wrong

`build/unwired-gate.sh` fired `load_project` and forgot it. The reply went to a file
nothing read, and the cleanup trap deleted that file on exit. So when the load failed, the
gate walked on and the NEXT call reported *"no project loaded"* — the consequence, two
steps downstream, with the cause already gone.

Measured during the v3.17.1 release, where it cost a diagnosis. The version bump meant
`org.jawata.mcp` depended on an `org.jawata.core:3.17.1` that `mvn package` had built but
never installed, so the importer's Maven resolve failed. The engine said exactly that, in
one precise sentence — and the gate threw the sentence away.

A gate that discards the one answer explaining its own failure makes every future failure
a fresh investigation.

## What it does now

The check reads the reply, and on a refusal prints the error code, the message and the
hint, states plainly that this is the CAUSE and *"no project loaded"* its symptom, then
exits 2 — the script's own code for did-not-run, which is not a pass. An unparseable reply
is treated as a failed load too, with the raw text printed, rather than falling through.

## Proven with a control

A check that always failed would satisfy the first case alone, so all three were run
against the block extracted from the shipped script:

| Input | Result |
|---|---|
| the real failure reply from the incident | names code, message and hint; exit 2 |
| a successful load | silent; exit 0 |
| an unparseable reply | exit 2, raw text printed |

The full gate re-run after the change is unchanged: 753 files examined, 78 findings,
baseline unchanged, PASS.

## Why the suite is not re-reported

The compiled code is identical to v3.17.1's, whose suite was 2103 tests with 0 failures on
the shipping tree, alongside a passing hollow-wiring gate and 84 end-to-end checks. Nothing
in this release can move those numbers. The release workflow runs all three again anyway.
