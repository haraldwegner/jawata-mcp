# jawata-mcp v4.0.3

## An updated catalogue entry no longer leaves its old copy behind

Every time a catalogue entry was rewritten from its source, the displaced copy was
marked `superseded` and kept. Nothing could ever collect it again: the per-item path
only iterates the addresses the current input names, and the orphan sweep reads live
rows only, so a superseded row was unreachable by both.

That made the leftovers grow with use rather than with renames. Any edit to an
entry's text stranded one row per pattern, per pass — ten passes over 187 patterns
would leave 1,870 rows nothing can read. Measured on a store that had been through
one address change and one content pass: **187 live catalogue rows and 187 stranded
ones**, half the catalogue unreachable.

**What changed.** The replacement, the orphan sweep and the retired-prefix migration
now REMOVE the row instead of marking it. A catalogue row is derived — its manifest
reproduces it exactly — so the copy a replacement displaces is a duplicate answering
the same address, not history anything can rebuild from. This is the catalogue lane
only; a hand-written experience is never removed by it.

**Stores that already carry leftovers heal themselves.** A seed now also clears the
superseded rows stranded under its own prefix, so the first catalogue load after this
upgrade removes them. Nothing destructive has to be run by hand, and `prune` — which
has no delete-by-id and once removed 101 entries for an asked seven — is not involved.

### Under it

- `ExperienceStore` gains `deleteByIds`, abstract so no wrapper can inherit a silent
  no-op. Removal is keyed on ids rather than the source reference because a leftover
  and the row that replaced it share a reference: a delete keyed on the reference
  would take the live row with the dead one.
- Two tests pinned the previous contract in the same words ("the incumbent must
  SURVIVE the edit"). Both now state the new one, each carrying the reason.
