## jawata-mcp v4.0.1

The v4.0.0 dogfood window's findings, shipped. Every item here came from using
jawata to ship jawata on release day, not from a review pass.

**A release stopped being an outage.** Publishing v4.0.0 made studio restart all
three residents at once, and each re-resolved every project's Maven classpath
from scratch: ~10 of 20 cores, load average 17, a machine unusable for minutes.
The cache for that work already existed and was already keyed correctly — by a
content hash of every `pom.xml` in the tree — but it was a static map that died
with the process. Its own javadoc said "once per JVM", and that clause was the
whole defect. At 290 repositories a restart is 290 Maven runs.

It now persists. The content-hash key is what makes that safe: a pom changes by a
byte, the key changes, the old entry is never asked for again — no invalidation
logic to get wrong. What the hash does NOT cover needed the real design: it
attests to the build files, never to the local repository the jars live in, so a
persisted entry can survive a purge of that repository and name jars that have
gone. Every hit therefore verifies the jars still exist and discards the entry
otherwise; without it the cache would hand back a classpath silently missing its
dependencies. The in-memory tier also rises from 64 entries to 512 — at 64 the
65th project evicted the first, on a machine holding 290.

**Two gates that were wrong about their own subject.**

The dist staleness guard asked whether any source was newer than the boot
launcher — the module that changes least often — so a build that correctly
rebuilt the changed bundle was called stale (measured: 14:52:03 for the rebuilt
bundle against 12:46:25 for the launcher). The proxy was unsound in both
directions: it would equally have passed a dist whose launcher rebuilt while a
bundle did not, which is the silent green about the previous build it exists to
prevent. It now references the oldest jar we build. The first attempt used the
oldest jar of any kind and its own control caught it — third-party jars carry
their upstream timestamps, so the oldest jar present is dated 2021, and that
version refused every correctly built tree.

The family-sweep deadline was a hang backstop priced as a latency budget. At 120 s
it sat close enough to real work that ordinary variation crossed it, failing
healthy sweeps with an assertion that reads exactly like a regression, on a
different test each time. It is now 600 s and overridable. `mcp#66` attributes
this to parallel suite load; CI run #45 refutes that — serial, one JVM, 1976 s,
same ceiling, different test.

**Version discipline.** The v4.0.0 bump missed three sample poms because the
sites were derived by grepping the *current* version, which by construction finds
only files that already agree; a module pinned to an older version is invisible
to that search precisely because it is inconsistent. All fifteen sites are
covered here, edited by line rather than by file — `4.0.0` is also Maven's model
version and appears in two URLs per pom, so a file-scoped replace corrupts every
one of them.

Sharded suite: 2246 total, 2244 succeeded, **0 failed**, 2 corpus-gated skips.
