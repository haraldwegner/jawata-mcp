# jawata v3.6.3

**Two macOS-visible faults, both with causes that were never macOS-specific.**

## The Java compiler never started on macOS

On a Mac, every project jawata imported got a Java runtime container that was
never bound to a JDK. Nothing about that was loud. Compiles came back with no
errors — because the compiler had no runtime to run against. No JDK type
resolved. Test discovery found nothing. A clean result meant "nothing was
looked at", which is the failure mode jawata exists to prevent.

The cause is one string. jawata asks JDT for its standard "VM install type" and
then registers the JVM it is running on. It asked using the type's **class
name**; the lookup matches on the **id the plug-in declares**, and those two are
different strings. So the lookup returned nothing, jawata logged that it could
not register a JDK, and gave up.

That was wrong on every platform. It only ever showed on macOS because Linux
and Windows never reach this code: JDT detects the running JVM by itself there
and jawata returns before the broken line. On macOS JDT deliberately detects
nothing and hands the job over — to this.

Fixed, and made harder to break: the lookup now tries the declared id and, if a
future JDT renames it, falls back to finding the type by its implementation.
A rename now costs a slower lookup instead of a silent loss of the compiler.

## Reading a library type crashed

`inspect(kind=source)` on a type from a jar with no attached source — a JDK
class, a dependency — returned an internal error instead of the signature-level
stub it promises. The class that produces that stub was not visible to the
tool's own bundle at run time, although it compiled. One missing package
declaration; now declared.

## A test that could report either answer

Releasing this found a third fault, in the test suite rather than the product.

A profiling test asserts that a CPU profile ranks a deliberately CPU-burning
method near the top. Its fixture is, by design, blocked about 97% of the time —
that is the whole point of it, since the test exists to show that "wall time"
and "CPU time" are genuinely different measurements. A CPU profiler samples
only threads that are running, so on a loaded machine five seconds of recording
can catch that fixture once or twice. Every row then ties at one sample, and the
ranking is arbitrary order among ties.

It failed the release build that way. Measured on a loaded machine afterwards,
it also does the opposite: the method came first with two samples, so the
assertion would have *passed* on data that supports no conclusion at all.

The ranking assertions now require the profile to have collected enough samples
to rank. When it has not, the test aborts and says so with the count, rather
than reporting an ordering it cannot justify. The half of that test which does
not depend on sampling — that the wall-time ranking is led by a blocking
method, which comes from recorded events rather than samples — was moved ahead
of the sampled half, so a thin recording no longer costs that proof.

The test runner had the matching gap: an aborted test moved a counter and
printed nothing about which test or why, because only failures were reported.
Aborts now print their reason.

## Verification

Full suite 1692 of 1695 passed, 0 failed. Three aborted, each stating its own
reason in the output: two need a private corpus, one is the profiling test
above declining to rank a two-sample recording. End-to-end suite against the
built artifact: 36 of 36.

Four new tests, and they run on Linux, which is the point. The previous two
macOS patch rounds shipped changes that could only be judged on the affected
Mac. These fail on the development machine without the fix: the VM type lookup
resolves, it is the right implementation, it accepts the running JVM's
installation directory, and — pinned deliberately — the class name is asserted
*not* to be a valid id, so the defect cannot be reintroduced by "simplifying"
the constant back.

The source-reading fix is verified through the product's own front door against
the built artifact, not in a unit test: a resident started from this release's
jar returns a disassembled stub where it previously errored.

**What is still unproven here.** The final step of the JDK registration — the
one that actually binds the container — runs only on macOS, so Linux cannot
execute it. Every input to it is now asserted; the binding itself needs one run
on a Mac.

Nothing about recall, the experience store, or the tool set changed; the tool
count stays 45.
