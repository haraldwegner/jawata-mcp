# jawata-mcp v4.1.2

One fix: a file reached through a symlinked directory now resolves.

## One directory under two names

Two refactorings failed on macOS and passed on Linux in the same test run. The cause is not
the operating system: on macOS `/var` is a symlink to `/private/var`, so a path handed in as
`/var/folders/…/x` and the same directory as the resource layer knows it are unequal to every
string comparison in this product while naming one file. Measured in the v4.1.1 run — 2376 log
lines carry the first spelling and 1906 the second, from one process, a project loaded from
`/var` whose workspace initialised at `/private/var`. Linux puts temporary files under `/tmp`,
which is not a symlink, so both spellings agree and the question never arises there.

The lookup every caller reaches — one method, 111 references — now retries once with the
canonical path when the direct comparison finds nothing. It runs only where the lookup had
already failed and would have returned null, so it can turn a miss into a hit and never the
reverse; canonicalising touches the filesystem and can fail on a path that does not exist,
which is why it is attempted second and never throws.

**This is the third instance of one fragility, and the cure is copied rather than invented.**
`HostPathsImpl.relativizeOrAbsolute` does exactly this two-step for the display side, and its
comment records the first two: a packaged build leaking its mount path, and nineteen Windows
comparison tests. What was missing was the same step where paths are compared for identity
rather than for display.

## The test that was said to be impossible

v4.1.1 shipped a different attempt at this, with a note that it could not be tested here
because "the timing window does not open on Linux". That was true of the fix and false of the
defect. The failing condition is a symlinked path, and Linux makes symlinks perfectly well —
macOS merely ships one where temporary files live. `SymlinkedPathResolvesTest` creates the
symlink macOS provides by accident, resolves one file under both names, and asserts they are
the same unit. Without the retry it is null.

The v4.1.1 attempt — settling the model before the compile gate reads errors — is left in
place. It is harmless and cheap, it was not the cause, and removing it in the same release
that replaces it would churn a path 111 callers reach for no gain.
